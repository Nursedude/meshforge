# The Aim Audit — putting weight on 314 green lights

> **Status**: planned 2026-09-09, not yet run. Pilot of 4 classes done (below).
> **Exempt from the harness freeze** (`.claude/rules/harness_restraint.md`): it
> adds no instrument. Its only outputs are deletions, narrowings, and honest
> relabelling. If it ever produces a new detector, it has failed.

## Why this is the domain's own method, not a new idea

`house of cards` has a precise local definition, from the 2026-06-19 post of
that name: **"a fix that holds only because nothing has leaned on it yet."**
And its closing line is the whole method — *"The difference between a house of
cards and a wall isn't how it looks when you finish. It's whether you've put
weight on it and watched it hold."*

By that definition the fleet's **314 `clean` readings are the house of cards.**
Not because they are wrong — because no weight has ever been put on them.

The lineage is already written and this audit only finishes it:

| post | lesson |
|---|---|
| 2026-05-29 *A clean payload is not a green light* | a bug in the gap between what a monitor READS and what it SHOWS |
| 2026-06-06 *The circuit breaker was decorative* | safety machinery that was not plugged in |
| 2026-06-08 *Make it fire* | "So we broke a box on purpose. The loop didn't react." |
| 2026-06-19 *House of cards* | a fix nothing has leaned on; the capture that "caught nothing — and that was the finding" |
| 2026-06-20 *Built not proven* | trust nothing until a controlled experiment makes it fail on purpose |

And it is the **missing half of an existing pair**:

| drill | kills | asks | status |
|---|---|---|---|
| `scripts/guard_drill.py` | plants a violation | does the GUARD fire? | built |
| `scripts/falsifiability_drill.py` | **the watcher** | would we notice its death? | built, measured 09-02 |
| **the aim drill** | **the watched** | does the watcher notice? | **never run** |

`falsifiability_drill` proves a probe CAN fire. Nothing has ever asked whether
it is POINTED AT ANYTHING. That is the unmeasured surface.

## The one question

From `calibrated_claims`, already written, never run across the board:

> **"What would still pass this check if the feature were dead?"**

If you can name something — a listening socket, an enabled-but-failed timer, a
fresh state file beside a crashlooped daemon — the check measures PRESENCE, not
FUNCTION.

## Scope (measured 2026-09-09)

- **61 distinct signal classes** over **9 boxes** = 314 `clean`, 234 `inert`,
  1 `indeterminate` (`parity_drift`, meshanchor-server).
- Audit the **61 classes**, not the 314 readings — aim is a property of the
  class. Per-box shape only matters where a class is `mixed` (39 of them).
- `oracle_delivery_degraded` is `inert` on all 9: handle as a deletion
  candidate, do not audit its aim.

## Method — bucket, then judge

**Step 1 (mechanical, cheap).** For each class, read what the probe actually
READS and assign ONE bucket. This is a fact about the code, not a judgement:

- **PRESENCE** — clean licenses only "it exists / it is running". `systemctl
  is-active`, a socket bound, a file present, a PID alive.
- **FUNCTION** — clean licenses "it did its job". A round trip completed, a
  counter advanced, a write landed, a message arrived.
- **HOUSEKEEPING** — the subject is a harness artifact (a notes file, a verdict
  log, an index, a soak fixture). Aim question does not apply; feeds the
  `harness` END tally instead.

**Step 2 (adversarial, the expensive part).** For every PRESENCE class, ask the
one question and then the one that matters:

> **Does anything downstream treat this class's `clean` as a FUNCTION claim?**

A PRESENCE probe is not a defect — `probe_service_inactive`'s own docstring says
plainly that it compares `systemctl is-active`. **The defect is a consumer that
reads its `clean` as "working".** That is exactly the 08-11 failure: `NRestarts=0`
was true while the web client served nothing. Consumers to check for each:
`honest_status.sh` legs, mini rule text, the `/fleet` surface, digest wording,
and any runbook or persistent_issues row that cites the class.

**Step 3.** Each class gets exactly one verdict, and only these four exist:

- `AIMED` — clean licenses what its consumers claim. No action.
- `PRESENCE-ONLY, HONESTLY LABELLED` — presence probe, no consumer overclaims.
  No action. **This is expected to be the largest bucket and is not a finding.**
- `OVERCLAIMED` — a consumer reads presence as function. **This is the finding.**
  Fix the CONSUMER's wording or add the function check — never both in one pass.
- `DELETE` — measures nothing any consumer uses.

## Pre-registered prediction (so the audit cannot be graded after the fact)

Written before the run, from a 4-class pilot:

- PRESENCE or HOUSEKEEPING: **55-70%** of the 61.
- `OVERCLAIMED` findings: **3 to 8.**
- **If the audit returns ZERO `OVERCLAIMED`, the audit was theater**, not a
  clean bill of health. Base rate says otherwise: today one gate's aim was
  audited (`harness_audit`'s session-notes leg) and it was misaimed — 1 for 1.
  Zero findings means the method was applied too gently; re-run it adversarially
  or hand it to a different reader.

| class | reads | bucket | note |
|---|---|---|---|

**Measured cost: ~3 min/class → 61 classes ≈ 3 hours of review attention**,
decomposable: step 1 is mechanical, step 2 is not.

## Who runs it — and why NOT me

**Recommend Fable 5.1 for step 2, and the reason is authorial distance, not
cost.** `calibrated_claims` ranks evidence by who wrote the witness: *"A witness
you did not write outranks one you did, because a check you author encodes only
the narrowness you already thought of — the defect is by definition outside
it."* **I wrote many of these probes.** I am structurally the wrong auditor for
my own aim, and today is the evidence: I have walked past
`probe_service_inactive` dozens of times.

Two hard constraints on that pass:

1. **FINDINGS ONLY. No fixes in the same pass.** This is the documented
   2026-09-03 brake — *Opus builds → Fable reviews + fixes + rolls its OWN
   unreviewed fix*. An aim audit that fixes what it finds re-runs that exact
   loop, and the fixes would themselves be unaudited. Fixes are a separate,
   separately-authorized pass.
2. **Step 1 may be delegated down** (Haiku/fast is fine — "what does this
   function read?" is mechanical). Step 2 may not.

## Stop conditions

- Any single class costing >15 min: record it as `NEEDS-FIELD-DRILL` and move
  on. A class whose aim cannot be judged by reading is a candidate for an
  actual break-it-on-purpose experiment, which is a different, larger job.
- If `OVERCLAIMED` findings exceed 12, **stop and report** rather than
  finishing. That result changes the plan and should reach the operator before
  more hours go into it.

## Output

One table, 61 rows, committed to `.claude/audits/`. Then the fix pass is
scoped from the `OVERCLAIMED` rows only, one commit per consumer, each tagged
with the END it serves in the calibration ledger's new `end` field.

*Slow wins the race.*
