# Manifest-lazy handler registry — design (Fable, 2026-07-14; Opus executes)

> Provenance: queued as "the deeper altitude fix" in the perf-arc self-review
> residuals (review_provenance 2026-07-13 row; `project_opus_handoff_2026_07_13`).
> Fable designed this per the model-advisor split: frontier designs, Opus
> executes. Startup today ≈421 ms with per-file import deferrals; this makes
> all ~100 handler imports lazy BY CONSTRUCTION and obsoletes the per-file
> `_load_x()` deferrals one class at a time.

## The problem shape

`main.py:95` does `for handler_cls in get_all_handlers(): registry.register(handler_cls())`.
`get_all_handlers()` (`handlers/__init__.py`) imports ~100 handler modules at
startup. `HandlerRegistry.register()` needs each handler's `menu_items()`
IMMEDIATELY (tag validation + `_tag_index` + menu construction) — that is the
only reason the modules must exist at startup. Dispatch (`_tag_index` hit →
`handler.execute(tag)`) is the first moment the module's CODE is needed.

**Insight**: menu metadata is static per commit. Move it into a generated,
checked-in manifest; import the module at first dispatch of one of its tags.

## Design

### 1. The manifest — `src/launcher_tui/handlers/manifest.py` (GENERATED, checked in)

```python
# AUTO-GENERATED by scripts/gen_handler_manifest.py — DO NOT EDIT.
HANDLER_MANIFEST = [
    {
        "handler_id": "rf_tools",
        "module": "handlers.rf_tools",        # import path (src/launcher_tui on sys.path)
        "class_name": "RFToolsHandler",
        "menu_section": "radio",
        "menu_items": [("rf_calc", "RF Calculator — link budgets", None), ...],
        "lifecycle": False,                    # True → eager (see §4)
    },
    ...
]
```

Generator: extend/refactor `scripts/gen_capability_index.py` (it ALREADY walks
the live registry to emit `capability_index.md`) into a shared walker with two
emitters — the markdown index and the manifest. One walker, two artifacts,
zero new drift surface.

### 2. Registry — `register_lazy(descriptor)` beside `register()`

- Validates tags/sections from the DESCRIPTOR (same duplicate-tag guard,
  verbatim — move the validation into a helper both paths call).
- `_tag_index[section][tag] → _LazyHandler(descriptor)` sentinel.
- `get_menu_items(section)` reads descriptor menu_items (flag NAMES are in the
  manifest; flag evaluation against ctx already happens at menu-build — no
  import needed).
- `dispatch(section, tag)`: on a `_LazyHandler` hit → `importlib.import_module`,
  instantiate, `set_context(ctx)`, **verify live `menu_items()` == manifest
  snapshot** (cheap equality; mismatch = stale manifest that dodged the gate —
  raise loudly, never dispatch on drifted metadata), swap the real instance
  into `_handlers`/`_tag_index`, then dispatch. Subsequent dispatches hit the
  real instance (one-time cost).

### 3. Honest failure paths (walk honest_failure_modes over this — it's a loader)

- Import error at first dispatch → the SAME honest ImportError dialog the
  perf-arc `_load_x()` pattern shows (name the module + the pip/apt fix), and
  the failure leaves a witness (log ERROR + `report_action(ok=False…)`). The
  menu item must NEVER silently no-op.
- A handler present in the package but MISSING from the manifest = dead UI →
  that is exactly `TestHandlerReachability`'s job; extend it to compare
  package-walk vs manifest (not vs `get_all_handlers()`).
- Manifest entry whose module/class no longer exists → generator fails; the
  drift gate (§5) blocks the commit.

### 4. Eager exceptions

- `lifecycle: True` handlers (any implementing `LifecycleHandler` hooks that
  must run at startup) are imported eagerly in a loop over
  `[d for d in HANDLER_MANIFEST if d["lifecycle"]]` — expected to be ~0-3.
- A handler whose `menu_items()` is genuinely dynamic at runtime CANNOT be
  manifest-lazy. The generator must detect divergence (call it twice / compare
  to source constants is overkill — the register-time equality check in §2 is
  the backstop) and the design rule is: menu metadata is static per commit;
  dynamic behavior belongs in feature FLAGS (already supported), not labels.

### 5. Drift gates (all existing machinery)

- Pre-commit already runs "Checking capability-index drift" — the same check
  regenerates/verifies the manifest (one walker, §1). Stale manifest = commit
  blocked, same as capability_index.md today.
- `TestHandlerReachability` pivots to manifest-vs-package-walk.
- New test: every manifest entry imports + instantiates + `menu_items()`
  equality (this is effectively today's startup cost moved into CI where it
  belongs).
- MF014 note: manifest carries no operator values (labels only) — no new lint surface.

### 6. Migration order (Opus, mechanical once §1-2 exist)

1. Generator + manifest + `register_lazy` + tests (no behavior change:
   `main.py` still eager). 2. Flip `main.py` to manifest registration behind
   env `MESHFORGE_TUI_EAGER=1` escape hatch. 3. Startup-leanness gate
   (`test_tui_startup_leanness`) ratchets down to the new floor. 4. Delete
   `get_all_handlers()`'s import list (keep the function reading the manifest
   for back-compat callers). 5. Retire per-file `_load_x` deferrals ONLY where
   they exist purely for startup (keep ones guarding optional deps).

### Payoff / cost

- Startup → backend + registry + manifest-parse (expect well under 421 ms;
  measure with the existing leanness gate, don't assert a number here).
- Cost: one generated file (~100 entries), one-time-per-handler dispatch
  latency (an import — the user just pressed a menu key; imperceptible), and
  the §2 equality check as permanent honesty tax (~free).

### Non-goals

- No plugin/discovery system, no entry-points, no dynamic menu labels.
- MA twin: MA's TUI has its own registry lineage — port the PATTERN after MF
  soaks, per twin-map tier rules; do not byte-port.
