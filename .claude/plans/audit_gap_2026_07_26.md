## ⚠️ How NOT to compute this (my first attempt, wrong)

I first harvested every SHA in the ledger and treated *"is an ancestor of some
ledger SHA"* as reviewed. That reported **8** unreviewed commits — off by an
order of magnitude, in the direction that falsely blesses code.

**Why it is wrong:** most ledger rows are **scope-limited**. Row 14 reviewed
`src/gateway/*` only; row 21 was the maps domain; row 13 is a named-commit
dude-claw diff. A commit touching `src/utils/` inside a gateway-scoped window
is an ancestor of that row's SHA but was never opened by it.

**Correct method:** only rows that explicitly reviewed a FULL window give
blanket coverage (they say so — *"the full unreviewed 37-commit window
`0a85896d..c17c611c`"*). Take the newest such row as the frontier; subtract
commits individually named by later scoped rows; everything else is unreviewed.

Both scripts are in this session's scratchpad pattern and trivial to rewrite;
the correct one is ~40 lines of `git rev-list` + `git show --numstat`.

**F2 — same class, systemic.** `_load_parity_streak` returns `0` on any error

## F3 — the upshift guard's leg 3 is silenced by the act of queuing (LIVE)

Found 2026-07-26, minutes after committing the queue row above — and caused
by it.

`review_provenance_check.py::_last_provenance_commit` resolves leg 3's
boundary as *the last commit that TOUCHED `review_provenance.md`*:

```python
_git(repo, ["log", "-1", "--format=%H", "--", PROVENANCE_REL])
```

That is "the ledger was edited", not "code up to here was reviewed". The two
coincide only when a row CLOSES a pass. When a row QUEUES work — the exact
path `model_advisor` tells a non-frontier session to take — the boundary jumps
to the queuing commit and the nudge resets to zero.

Measured immediately after `2376e20c`:

```
leg-3 boundary:            2376e20c   (the commit that queued 12,240 unreviewed lines)
src lines since boundary:  0
TRUE unreviewed src churn: 4,752      (c17c611c..HEAD -- src/)
```

**Writing down that work is unreviewed is what persuades the guard it is
reviewed.** The louder you are about the debt, the quieter the nudge. Legs 1
and 2 (the HARD gates) are unaffected — they key off row CONTENT, not this
boundary — so nothing false can be *claimed*; the failure is that the advisory
that exists to surface accumulating unreviewed code goes quiet exactly when
the debt is being recorded.

NOT fixed here: the fix is a design decision about what "boundary" should mean
(last row that CLOSED a pass? a per-row scope-aware high-water mark? the
blanket-window rule this document uses?) — and it is a change to the gate that
polices reviews, so it wants the frontier tier rather than my guess.
Suggested direction: distinguish closing rows from queuing rows (the completed
TABLE vs the worklist), and take the boundary only from the former.
