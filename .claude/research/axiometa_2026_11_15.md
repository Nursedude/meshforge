# Axiometa (Genesis boards, AX22 modules, Studio): research 2026-11-15

## Verdict

- **What it is:** a one-founder maker/STEM ecosystem. There are ESP32-S3 "Genesis" boards (Mini: 4 AX22 ports, 3xAA/AAA; One: 8 ports, LiPo) and snap-in 10-pin AX22 modules. The **"LR1262" LoRa module is an Elecrow SX1262 carrier** (not a Semtech LR11xx). Axiometa Studio is a cloud-hosted, AI-first web IDE ("Axie"). It compiles on Axiometa's build server and flashes from the browser over WebSerial with esptool.js.
- **Where it could matter most here:** the Genesis Mini + LR1262 is an **upstream Meshtastic target** (`variants/esp32s3/axiometa_genesis_mini`, merged 2026-09-18). That makes it a candidate for a cheap, stock-firmware, receive-only **second witness** in CLAW-1. Studio is not needed for that.
- **Biggest risk:** Studio's AI loop can call `flash` on any board the tab has a WebSerial grant for, with **no per-flash confirmation in the client handler**. It uses server-built images and a server-set `erase_all`. It also POSTs project code and (per the client code) the Wi-Fi config to a Railway-hosted backend. Never run Studio with a fleet radio plugged in.

## 4. Domain fit (MeshForge)

**Fits**
- **CLAW-1 witness hardware, stock firmware.** The Genesis Mini + LR1262 SX1262 is an upstream Meshtastic target, and the board costs $27.99 + $23.99. Q2 says "one Heltec V4 + one Pi" for a ham. This would be a second, independently built SX1262 witness, which is useful for Q7 "WITNESSES DISAGREE": a witness with a different front end and antenna is a better control than a second Heltec. It runs on 3xAA, so it can sit on a mast with no USB power.
- **Standalone-bar teaching kit.** "Works as a classic Arduino dev board" plus Arduino IDE means a ham with no AI can use it. Studio is optional.
- **Headless MCP as dev tooling** (not product). An operator could let a Claude Code session compile and flash a *bench* Genesis board. That is dev-with-Claude, which the bar allows, but see the risks.

**Does not fit**
- **Studio in the product path.** It is cloud-only (Railway + Supabase), account-bound, closed-source and has no pricing. That contradicts "a ham with no AI can run it", "AI assist is optional, user-configured", and an ECOMM kit with no WAN.
- **RNS/RNode and MeshCore:** no upstream target. Making one means maintaining a fork with a no-NRST radio on a shared SPI bus that the display also uses (the variant documents the LovyanGFX/RadioLib bus-sharing hazards).
- **A 24/7 witness without hardware radio reset.** NRST is tied off, so a radio wedge needs a power cycle. The Heltec V4 does not have this limit. (BELIEVED, from the variant comment.)
- **HAT or fleet radio replacement:** none. Alkaline power with no charger and no GPS makes it a bench or temporary-node part.

**What would have to be true to adopt it**
1. A Genesis Mini runs **stock upstream Meshtastic** (Meshtastic web flasher, not Studio) on the HawaiiNet channel and is heard by a fleet node. That would be measured at both ends, not read from docs.
2. The LR1262 band and antenna connector are confirmed on the physical module. That is the operator's to read; the product pages were unreadable to me.
3. The design files are actually published under the claimed CERN-OHL-S (a repo or download), not just asserted.
4. For any Studio or headless use: a written box rule that **only a dedicated bench board, never a fleet radio**, is attached to a machine with a Studio tab or the axiometa MCP server.

## 5. Risks

- **An AI that can flash a radio.** The `flash` tool runs a server-built image, can `erase_all`, and asks the user nothing per flash (BELIEVED from the handler code). A board with a granted WebSerial port is re-flashable by the model's decision.
  - On a radio this can wipe channel keys and identity in NVS, push an image with any region or TX power, and the image is not reproducible locally.
  - On a box like VolcanoAI, where a 303a:1001 device is attached, a Studio tab granted that port could re-flash whatever it is.
- **Cloud dependency and lock-in.** Studio's compile, AI and project storage are all remote. The headless key is per account. If Railway, Supabase or the company disappears, Studio stops (BELIEVED). The hardware is not locked: Arduino and upstream Meshtastic work without it.
- **Data egress.** Code, chat, files and (per client code) the Wi-Fi SSID and password go to the backend. The privacy policy does not cover Studio. The AI provider is unstated.
- **Bus factor and maturity.** One founder, "brand new … moving fast", Studio source not public.
- **Regulatory.** The FCC/CE claim covers the Elecrow module only. TX power and region in AI-generated firmware are not reviewed by anyone. Part 15 compliance becomes the user's problem the moment the AI writes radio code (BELIEVED).
- **Supply.** Stock status is UNKNOWN; one homepage item showed "sold out" (a display, not the radio).

### Verdict

- **What it is (VERIFIED):** a pip package (`axiometa-cli`, MCP server `python -m axiometa_cli mcp`)
  plus an account-bound key minted in Studio. The agent gets **nine** tools: board/part lookups,
  `list_devices`, `read_serial`, `provision`, `compile`, `upload`. Compiling and flashing happen
  **locally**, with a private arduino-cli under `~/.axiometa`. Board knowledge (pins, fqbn,
  boards.txt fragments, variants) is **fetched at runtime from `cli.axiometa.io`** with the key.
- **Biggest risk on a box with a fleet radio on USB (VERIFIED from code):** `upload` and
  `read_serial` with no `port` take the **first enumerated serial port, with no VID filter and no
  confirmation** (`core.py:163-179`). `upload` then runs compile plus `arduino-cli upload -p <that
  port>` (`core.py:421-424`). Detection also labels any Espressif VID `0x303A` device as a
  "genesis-one/genesis-mini/xiao-shield-esp32s3" candidate (`detect.py:18-21`).
  - **On this box, VolcanoAI, `/dev/ttyACM0` right now is VID 303a PID 1001, an "Espressif USB
    JTAG/serial debug unit" (VERIFIED, from sysfs).** It is the only USB serial device, so it is
    exactly what an unqualified `upload` would flash. I have not identified which device it is
    (UNKNOWN).
  - A native-USB ESP32-S3 Meshtastic or RNode radio would be overwritten. The agent decides when
    to call `upload`; the tool itself never asks.
- **Can it be used safely?** Yes, on a **bench-only machine** with **no fleet radio, RNode or HAT
  attached**, run as a normal non-sudo user (BELIEVED, reasoned from the code). How:
  1. Use a dedicated machine or VM with only the Axiometa board passed through.
  2. Install it into its own venv. Never use pip on an apt-managed fleet box.
  3. Register it `--scope user` on that machine only, never on `/opt/meshforge` hosts.
  4. Always pass an explicit `port=/dev/serial/by-id/...` in prompts, and require Claude Code
     permission prompts for `upload` and `provision` (do not allow-list them).
  5. Revoke the key in Studio when done.
- **Never on a fleet host.** Every compile runs a boards.txt that a remote server supplies, so an
  install is a standing remote code path (see the trust note below).

### Network calls and data sent (VERIFIED: an exhaustive grep of urlopen and subprocess sites)

1. `GET cli.axiometa.io/api/knowledge/boards`, with `Authorization: Bearer <key>`, at most once
   per run (`knowledge_client.py:86-91`).
   - The response `files{rel: content}` is written under the cache. The relative paths are **not
     sanitised** (`:104-107`), so a hostile or compromised server could write outside the cache
     dir. That is a path-traversal class, BELIEVED from pathlib semantics, not tested.
   - It also returns `cli_latest`.
2. `GET cli.axiometa.io/api/ping` with the key and an `X-Axiometa-CLI: <version>` header. It fires
   on **every MCP initialize**, on a background thread, and the code calls it "analytics"
   (`knowledge_client.py:51-64`, `mcp.py:371-378`).
3. `GET downloads.arduino.cc/arduino-cli/arduino-cli_1.5.1_<os>.tar.gz`, **with no checksum or
   signature check**, then `tarfile.extractall` with no filter (`toolchain.py:209-239`).
4. Through arduino-cli: the Espressif index (raw.githubusercontent.com), the Seeed index
   (files.seeedstudio.com), the Arduino library index and core/tool archives.
   - arduino-cli checks archive checksums against the index (BELIEVED, standard arduino-cli
     behaviour). The index URLs can be overridden by env (`ESP32_PACKAGE_INDEX_URL`,
     `NRF_PACKAGE_INDEX_URL`).
5. PyPI, for `adafruit-nrfutil`.
6. `AXIOMETA_BACKEND` overrides host 1 (`knowledge_client.py:73-74`).

- **What is sent to Axiometa:** the key, which identifies the account and, per the README, encodes
  `user_id:key_id:issued_at`; the CLI version; and implicitly IP and timing. **Sketch source,
  binaries, serial output and the device list are not sent** by any code path in 2.0.2 (VERIFIED by
  the absence of other network sites).
  - Your agent's own provider does see all tool results, including serial output (BELIEVED).
- **Trust note (BELIEVED, from the Arduino platform spec):** board fragments in the fetched
  knowledge are appended to `boards.txt` (`provision.py:185-187`). Board-level properties can
  override `recipe.*` and `tools.*.upload.pattern`. So the server effectively chooses the commands
  run at compile and upload time.

### The key (VERIFIED from README plus code; server behaviour BELIEVED, README claims only)

- **Format:** `axm_<base64url(user_id:key_id:issued_at)>.<hmac-sha256>`.
- **Server side:** an HMAC check first, then a revocation and usage lookup by `key_id`.
  - Stated purpose: it authorises the board-knowledge fetch, plus the ping (usage).
  - There is no flash or compile authorisation, since that is local.
  - The README says that with no server secret configured "the service stays open".
- **Where it lives:** `AXIOMETA_KEY` env (the MCP config puts it in `~/.claude.json` for user
  scope), else `~/.axiometa/key` with mode 0600.
- **Without a key:** the cached knowledge still serves offline after the first fetch
  (`knowledge_client.py:77-127`). The module docstring says "No account, no auth" (`:9`), which
  contradicts the README. Live enforcement is UNKNOWN; I did not test it.
- **Revocation:** Studio's Revoke button. Revoking blocks future fetches but not the local
  toolchain or the cache (VERIFIED code: cache fallback).

### Port selection and flashing safety

- `core.list_ports()` is pyserial `comports()`. Without pyserial it globs `/dev/ttyACM*`,
  `/dev/ttyUSB*`, `/dev/tty.usb*` (`core.py:154-160`).
- `pick_port` and `serial_port` return `ports[0]` (VERIFIED, `core.py:163-179`). Linux ordering
  puts ttyUSB* before ttyACM* (BELIEVED, from pyserial).
- It does **not** touch every port, only the first one, and a confirmed board identity is **not
  required**. The `onboard` UART flag in `detect.py` only labels; it does not exclude.
- Board-fixed ports come from server data (`host_interface.serial_port`, `core.py:175`). The Pi
  HAT board uses `/dev/serial0` (README), and **`/dev/serial0` exists on this box** (VERIFIED).
- **Failure modes I believe likely on a fleet box (BELIEVED, not drilled):**
  - An esp32 fqbn against a native-USB ESP32-S3 radio flashes over Meshtastic or RNode firmware.
  - The xiao-shield-nrf52840 target uses Adafruit-bootloader DFU via nrfutil, the same bootloader
    family as RAK4631. It could reflash a RAK radio.
  - `read_serial` holds the port, which can collide with meshtasticd or rnsd ownership, and
    `reset=true` reboots the radio.
  - Whether the Axiometa fqbns use 1200-bps-touch is UNKNOWN (server data).
- There is no lock, no ownership check, no "is another process holding this tty" check, and no
  prompt (VERIFIED: no `input()` or confirm anywhere in the package).
