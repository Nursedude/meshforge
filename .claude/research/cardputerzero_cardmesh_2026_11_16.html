CardputerZero for MeshForge

M5Stack's CardputerZero is a pocket Linux computer, and its Cap LoRa-1262 adds an SX1262 radio on SPI. That combination is the same shape MeshForge already drives on a Pi. This page reads maxhayim/CardMesh and the other projects already building for it, compares the device with our earlier hardware studies, and maps where it fits the roadmap queue.

Companions: Axiometa for MeshForge · Femtofox mPWRD-OS Rebuild · Why Choose Us Over N · MeshForge Roadmap

Verdict

MeshForge can support this device with little new code, and the parts that need new code are the parts we are best at.

The upstream Meshtastic repo already ships a meshtasticd config for this radio (bin/config.d/lora-cardputer-zero.yaml, present on develop today). MeshForge configures meshtasticd on SPI hats now, so the radio path is mostly a template. What upstream leaves out is the part where devices silently fail: the YAML cannot switch on the Cap's power rail or its I/O-expander gate, so meshtasticd can start "active" with a dead radio. Catching that is MeshForge's core habit.

The larger opportunity is different. CardMesh is a pocket console for a server (MeshMonitor). A pocket console that shows the life of one message across two meshes is the one screen the roadmap says we should be best at (BIC-2, SHOW-1). That idea belongs in NEXT after BIC-2 ships, not before it.

What CardMesh's code shows

  • Good discipline that matches ours. DEVICE_BUILD.md separates what was verified from what was not, and the 11-16 commit messages give the root cause of each hardware bug, for example lv_timer_handler() returning UINT32_MAX and being used as a sleep, which froze the UI for about 49 days. Its README rules say "never fabricate unavailable values" and "never show ACK unless the data supports it."
  • The README is behind the code. It still says direct LoRa is "planned, not yet implemented", while commits f1326b5 through 5c13ff1 implement it. VERIFIED from the clone.
  • Radio parameters are hard-coded to US915 MediumFast, 20 dBm, on one public channel (MeshtasticWorker.cpp). A LongFast mesh such as HawaiiNet would hear nothing from it until that is configurable.
  • It is a minimal Meshtastic stack. It decodes text and position, broadcasts only, does not relay, does no PKI DMs and generates its own random node number. That is a reasonable pocket client, but it is not a full node.
  • Sent means transmitted. A message is logged as sent when radio_.send() returns true. Nothing says "heard". This is the same gap as our BIC-2 work, in a smaller form.

Radio ownership is the real hazard. CardMesh's direct-LoRa worker and meshtasticd both open /dev/spidev0.1 and toggle the same power rail and gate bit. Whichever starts second either fails or corrupts the other's state, and CardMesh's restore() on exit would switch the rail off under a running meshtasticd if it was the one that turned it on. This is our Issue #29 class (two owners of one radio), on new hardware. BELIEVED from reading both code paths; not run.

The pattern. Each new board arrives with an upstream config written by people who own the hardware. MeshForge's copies of those configs drift (Femtofox), and the part upstream cannot express in a config (power, gates, radio ownership) is where devices fail with no message. So MeshForge keeps up with new hardware by reading upstream as the source of truth and adding checks for what the config cannot say, not by writing more templates by hand.

Three ways MeshForge can work with it

Path A · build now, small

A CardputerZero as a MeshForge box

meshtasticd with the upstream preset, configured from MeshForge's existing SPI-hat flow. MeshForge adds what the YAML lacks: a pre-start step that turns on the rail and gate and restores them, and a check that the SX1262 actually initialised (journal init line, NRestarts), not just that the unit is active.

Fits: honest_failure_modes 1–2, MF018, INST-1 (role-aware installer).

Path B · after BIC-2

A pocket screen for a MeshForge hub

CardMesh already speaks MeshMonitor's /api/v1/sources/{id}/… REST shape. MeshForge already serves /api/inbox, /api/radio/nodes, /api/radio/channels and /api/gateway/delivery. A thin, read-mostly facade in that shape would let CardMesh show a MeshForge hub with no CardMesh changes. Each mesh MeshForge sees becomes one "source".

Fits: BIC-2, SHOW-1. Limit: one screen (a message's legs), not dashboard breadth.

Path C · lab, with the operator

A witness you can carry

"Measure at both ends" needs a far end. A handheld that logs RSSI and SNR per packet (CardMesh's planned Field Mode) is that far end for range walks and antenna comparisons, and an independent SX1262 front end for CLAW-1's "witnesses disagree" case.

Fits: CLAW-1, R2 / R8 measurement, the meshforge skill's RF rule.

Proposed NEXT rows (draft, for the operator)

  1. HW-SYNC: templates come from upstream

    Generate templates/available.d/ from the meshtasticd package's /etc/meshtasticd/available.d (or the pinned upstream bin/config.d) instead of hand-copying, with a test that fails on drift. This fixes the Femtofox pins and brings in lora-cardputer-zero.yaml for free. Red-first: a test that reads today's femtofox template and fails.

  2. HW-PRE: a pre-start hook for what YAML cannot say

    A small declared table of per-board pre-start actions (rail on, gate bit set, restore on stop) run by an ExecStartPre/ExecStopPost drop-in, plus a probe that reads the SX126x init line and NRestarts. Without it, a dead radio reads healthy (honest_failure_modes 2).

  3. HW-CPZ drill: one device, both ends

    CardputerZero on HawaiiNet LongFast, a fleet node at the other end: text both ways, RSSI and SNR read at both ends, rail restored after systemctl stop and after SIGTERM. Only then does the TRUTH-1 row say "proven". Needs the operator and the hardware.

  4. POCKET-1 (LATER, after BIC-2): MeshMonitor-shape read facade

    Read-only /api/v1/sources, …/nodes, …/channels, …/messages over MeshForge's existing data, token auth, loopback or LAN by default, parity-tested against MeshMonitor's real responses. Send stays off until BIC-2's truth is on the screen.

How the domain keeps up with hardware

Hardware now moves faster than one ham can buy it. The answer is a short, repeatable intake, not more templates.

  • Watch the source, not the press. One watch list: upstream bin/config.d/ and variants/ in meshtastic/firmware, the RNode_Firmware board list, MeshCore variants, and the client repos for any board we adopt. A new file there is the signal. Fold it into the existing landscape cadence (research/landscape_*.md) rather than a new process.
  • Ask five questions per board. Is there an upstream target or config? Who owns the radio? What can the config not express (power, gates, reset, RF switch)? How much RAM is left with meshtasticd running? What band is the front end actually rated for?
  • Upstream is the source of truth; we add checks. We sync configs and write probes for what they cannot say. We never fork a vendor config.
  • A board is "supported" only after a two-ended drill. Until then the in-app row says "unproven" (TRUTH-1).
  • Keep the fleet NEVERs. A CardputerZero runs its own meshtasticd version; that does not license rolling meshtasticd on fleet boxes. Before shipping a pinned meshtasticd, run objdump -T on it and look for pthread_detach, and stay on apt, not pip.

Being part of this, 1 + 1 = 2

One ham and one AI is the same size as every team in the table above. CardMesh is one developer working with AI assistants (its README has a section for them), and MeshMonitor's commits carry Claude co-author lines too. The useful contribution is the thing those projects lack: two-ended measurement on a real mesh, and honest labels for what was not measured.

Risks and blind spots

  • UNKNOWN Whether MeshForge's Python stack plus meshtasticd fits in 512 MB on a CM0. Measure the way the Femtofox guide did (peak RSS against MemAvailable) before choosing a profile.
  • UNKNOWN Whether the PR #12341 preset text on develop is final. The file is present; the GNSS follow-up is still open.
  • BELIEVED The 868–923 MHz rating, the $138 price and the November ship date each come from a single source.
  • BELIEVED Two programs fighting over the SX1262, from reading code. Not reproduced.
  • NOT CHECKED RNS. There is no RNode firmware for a Linux SPI SX1262, so on this device Reticulum would ride Wi-Fi or Ethernet (TCP), not the Cap. RNS-over-LoRa stays on RNodes.
  • NOT CHECKED Trail Mate's licence and code, the CardputerZero emulator, and the stock OS's glibc version.
